# Orchestrator

## 主会话职责

用 `/skill:orchestrator <任务>` 启动。调用 Skill 的主会话承担指挥职责，沿用当前模型，每次只维护 1 个执行者；每次派工都使用全新上下文的执行者。

- 主会话负责用户目标、任务边界、架构决策、整合与最终验收；执行者负责范围内的完整结果。按用户实际授权派工，不扩大授权范围。
- 仅在委派或并行确有收益时拆分任务。共享写入区和紧密耦合的契约保留一个负责人，避免重复调查、编辑和检查。
- 只调查决定范围和方向所需的上下文。具体实现和细节调查由执行者负责。
- 默认只读项目文件。执行者是当前任务的唯一写入者；只有确认执行者已停止写入，并记录写入权转移后，主会话才可接管编辑。

## 通知驱动，不阻塞等待

启动或投递返回后，主会话继续不依赖执行结果的工作。没有可推进事项时，报告当前状态并结束本轮响应，由通知触发后续处理。结束本轮不代表任务完成，保留任务记录和仍在工作的执行终端。

- 以执行者的 `hc send` 回报和 `hc` 的阻塞、错误、退出通知推进任务。保留默认通知，不使用 `--no-notify`。
- 不调用 `hc wait`、`hc send --wait`，不用 sleep、定时轮询或反复读取终端等待结果。
- 收到通知、用户要求查看进度或需要恢复异常时，才按需查询状态和读取终端。通知只触发核查，不作为任务完成或验收通过的证据。
- CLI 不上报 OSC 7501 时，`hc` 状态可能为 `-`。这不代表空闲或完成，也不能保证收到阻塞通知。依靠执行者的 `hc send` 回报和进程退出通知推进；回报不可达时记录缺口，不改成轮询。
- “仅终端回报”模式下，说明主会话无法接收主动回报，由用户请求或会话恢复触发结果收取，同样不阻塞等待。

## 执行者配置

根据用户指定的 CLI 选择角色；未指定时仍用 Pi。CLI 名可以放在任务前，例如 `/skill:orchestrator codex <任务>`。指定的 CLI 不可用时报告阻塞，不自动换用其他 CLI。

| CLI | 角色文件 | 身份核验 |
| --- | --- | --- |
| Pi（默认） | [worker.md](roles/worker.md) | 当前 shell 工具注入的 `PI_*` 会话值 |
| Codex CLI | [worker-codex.md](roles/worker-codex.md) | 当前会话的原生状态或运行时元数据 |
| Antigravity CLI（`agy`） | [worker-agy.md](roles/worker-agy.md) | 当前会话的原生状态栏或运行时元数据 |

开始前完整读取选中的角色文件和[共享执行约定](roles/instructions.md)，子会话接收两者的正文。角色文件的 `command` 定义 CLI、模型及可选 provider 和思考级别；修改对应文件即可调整配置。

角色路径从 Skill 目录解析，传递文件时使用绝对路径。选中角色以外的配置不参与本次派工。角色文件由本 Skill 加载，不会自动注册成 `hc` 全局模板。

## 1. 准备派工

先阅读并遵循 [herdr-core](../herdr-core/SKILL.md)。终端启动、投递、通知、恢复和清理按它要求读取的 `hc --skill` 执行。等待策略以本 Skill 的通知驱动约束为准，不采用手册中的阻塞等待示例。

1. 检查所选 CLI 的可执行文件、版本和本地 `--help`，确认支持角色要求的选项。按下表核对模型配置；缺失程序、选项不兼容或目标模型不可用时，暂停该次派工，保留指定配置。不要自行安装、升级或替换模型。
2. 阅读项目约定和决定任务边界所需的上下文。记录起始工作区差异，供验收区分既有改动与本次产物。
3. 从当前对话提取目标、已定方案和用户授权。只追问会改变目标、权限或验收的未决事项。

| CLI | 派工前核对 |
| --- | --- |
| Pi | 用 `pi --list-models <模型 ID>` 核对角色指定的 provider 与模型，保留原有严格检查。 |
| Codex CLI | 必须支持并保留 `--no-daemon`。本地版本支持 `codex debug models` 时，用模型目录核对目标模型和 effort；否则记录目录预检缺口，由启动后的当前会话证据核验。 |
| `agy` | 用 `agy models` 核对模型 ID、显示名和可用 effort 变体。确认支持 `--model`、显式指定的 `--effort` 及 `-i` / `--prompt-interactive`。 |

模型目录只证明可选配置，不证明实际运行身份。启动后仍须核对执行者提供的当前会话证据；CLI、模型及显式指定的 provider 和思考级别无法核实时，执行者只回报阻塞，不开始任务。非 Pi CLI 不使用继承的 `PI_*` 变量作为身份依据。

完成条件：启动条件与模型目录预检结果已记录，任务边界、用户授权和可观察的完成条件明确。实际运行身份留待启动回报确认。

## 2. 下发可验收任务

把下面任务书填成实际值：任务填在 `<task>` 里，授权单独填在 `<authorization>` 里，两者都与角色文件及共享执行约定的 `<file>` 块分开。任务书只补本次任务信息，不复制整段聊天历史。

```text
<task>
## 目标与产物
- 任务 ID：
- 目标与产物：
- 完成条件（每条自带验证与证据）：
  1. <可观察的完成结果> — 验证：<方式> → 证据：<预期输出>

## 方案与边界
- 已定方案：
- 兼容要求与非目标：
- 项目绝对路径：
- 可修改范围：
- 已有改动（起始差异）：

## 上下文
- 相关文件与关键约定：
- 已知证据：
- 需交由主会话决定的事项：<仅本次任务特有的决策事项及触发条件>，无则写“无”

## 执行与回报
- 回报地址：<主会话 HC_TERMINAL_ID 的实际值>，没有则写“仅终端回报”
</task>

<authorization>
- 文件修改：
- 测试编写：
- 测试修改：
- 测试运行：
- 依赖安装：
- 提交：
- 推送：
</authorization>
```

必要验证不扩大已有授权。需单独授权却未获准的验证，记录缺口与影响，不执行该项验证。

执行者不复用。首次派工、返工、补做和恢复都新开会话，从全新上下文开始；已有会话只用于收取结果，不再接收新的任务书。上一轮的已定方案、缺口、证据和已接受改动写进任务书传递，不依赖旧会话的记忆。

启动时按 herdr-core 检查已有模板。只有启动命令、角色约束和目标 CLI 的首条消息投递方式均匹配时才复用，否则直接启动角色文件的 `command`。复用模板只复用启动配置，不涉及旧会话上下文。

把选中角色的完整内容（含 `command`）和共享执行约定分别放进带原始绝对路径的 `<file path="...">` 块，再附上 `<task>` 与 `<authorization>`，合成首条消息。不要依赖 `@<路径>` 在其他 CLI 中自动展开。内容过长或无法安全传参时，用获准的临时派工文件保存完整内容，并在首条消息中给出绝对路径、要求完整读取。执行者无法读取时先回报阻塞，不自动扩大工作区访问权限。

直接启动时，按 shell 引号规则将 `command` 拆成程序与参数，保留全部选项和参数值。通过 `hc run --bg --outlive-parent` 设置项目工作目录和唯一终端名，按下表传入首条消息。

| CLI | 首条消息传法 |
| --- | --- |
| Pi | 在 `command` 参数后追加首条消息，作为一个位置参数。 |
| Codex CLI | 保留 `--no-daemon`，在 `command` 参数后追加首条消息，作为一个位置参数。 |
| `agy` | 在 `command` 参数后追加 `-i`，再把首条消息作为 `-i` 的值。用 `herdr_start` 时，将 `-i` 放在 `argv` 末尾，首条消息放在 `task`。 |

始终使用全新、本地、交互式会话。不要用 `pi -p`、`codex exec`、`agy -p` / `--print` / `--prompt`，也不使用 continue、resume、fork 或远程 agent 模式。复用模板时同样传递完整角色、共享约定和任务书，不能只套用模型命令。

启动成功只证明终端存在。若 `hc` 返回 `first_message.sent: false`，先读取终端确认原因；送达状态不明时也先核实，避免重复提交。信任或权限弹窗需要用户决定，不用 `--force`、跳过权限选项或修改持久配置绕过。

保持单执行者：启动新执行者前先收取旧执行者的结果并清理旧终端。

在主会话保留任务记录：任务 ID、CLI 与角色文件、本次采用的 `command`、实际运行配置及核验依据、执行终端与原生会话 ID、当前状态、写入者、证据位置和未决项。CLI 不暴露原生会话 ID 时标为“未暴露”，单独记录终端地址，不能把两者混为一谈。状态变化时更新，任务书保留为该任务的目标与授权依据。

消息送达不等于读取、采纳或批准。

完成条件：已有唯一执行终端，角色、共享约定与本轮任务已送达；执行者回报的实际 CLI、模型及显式指定的 provider 和思考级别匹配，且已开始本任务。按角色要求核对运行时证据，不能只接受启动命令的复述。以上确认由回报异步推进；未核实前记录为“待确认”，不为等齐回报阻塞当前轮次。

## 3. 验收与定向返工

收到执行者的完成回报后，按 herdr-core 收取结果并开始验收。主会话读取实际文件、差异和检查结果，逐项核对任务书。与起始差异对照，确认本次改动没有覆盖既有工作。

只向相关负责人发送会改变其行动的信息，不转发整段协作记录。

- 达标：把本任务标记为已验收，再检查完整用户请求是否还有遗漏。
- 有缺口：向新的执行会话派发返工任务书，附缺口位置、证据、期望行为、完成条件和已接受改动的文件位置。保留已接受的改动，不重做整项调查。
- 连续 2 轮返工无新证据或无实质进展：主会话重查假设、方案与任务划分，再给出调整后的任务。涉及目标、权限或显著成本变化时才向用户确认。
- 阻塞：记录原因与恢复条件，只暂停受影响的范围，不再向该会话派工；不受影响且已获授权的部分另行派工给新执行者。子会话报告不构成新的用户授权。

超时或中断不转移责任与写入权，也不授权取消任务。先查原终端状态和实际产物，再按 herdr-core 恢复；任务是否送达不明时先核实，避免重复执行。旧会话无法继续时，确认其已停止写入，再把任务书、任务记录和实际产物交给新会话继续，不恢复旧上下文。

上下文恢复后先读任务记录与任务书，核对执行终端、CLI、可用的原生会话 ID 和实际运行配置再继续。

完成条件：已授权且未受阻的任务均已通过逐项验收；其余项有具体阻塞原因与恢复条件。仍可推进的缺口继续返工。

## 4. 交付与清理

对照完整用户请求汇总已验收产物、文件位置和检查证据。交接时提供可用产物、证据、真实缺口和下一步负责人。

检查通过不能替代行为验收；必要检查未获授权或无法执行时，说明缺口与实际影响，不宣称完整验证。

仅在执行者承担的任务均已验收、所需结果已收集后，按 herdr-core 清理本次创建的执行终端。尚待返工或仍有阻塞的项转入新的派工，旧会话在结果收齐后清理。

完成条件：完整请求已逐项验收或有明确阻塞，检查缺口和恢复入口已说明，已完成工作的自建终端已清理。
